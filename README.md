# visa-duty-bot

Система мониторинга свободных слотов VFS Global для подачи на студенческую
визу Италии (D Visa Study) в визовых центрах Казахстана.

## Текущий статус

Все процессы запускаются и работают сквозным циклом: планировщик отбирает
цели, воркер идёт на сайт, результат пишется в журнал, сравнивается с
предыдущим и при изменении картины порождает уведомление в Telegram.

До боевых проверок остался **один шаг** — заполнить селекторы календаря
в `config/vfs_selectors.json`. Пока они пусты, парсер честно возвращает
`SITE_CHANGED` вместо того, чтобы месяцами выглядеть как «слотов нет».
См. [«Что осталось»](#что-осталось).

Состояние до переработки под ТЗ сохранено тегом `v0.1-duty-coordination`.

## Как выполняется проверка: две стратегии

Проверка идёт по цепочке, и вторая стратегия подхватывает, если первая
не сработала. Каким путём получен результат — видно в журнале (`strategy`).

| | Короткий путь (`direct`) | Длинный путь (`wizard`) |
|---|---|---|
| Что делает | один запрос дат внутри открытой сессии | проходит экраны мастера записи |
| Стоимость | одно обращение | 5–6 загрузок страниц |
| Когда применяется | когда известен адрес запроса дат | всегда, когда короткий не удался |
| Побочная польза | — | находит адрес запроса для короткого пути |

Смысл не в скорости. Каждая загрузка экрана `schedule` — повод показать
CAPTCHA (она включена там в конфигурации приложения VFS) и лишний след для
антибота. Прямой запрос внутри уже открытой сессии и дешевле, и незаметнее.

**Адрес запроса система находит сама.** Пока идёт длинный путь, воркер
слушает сеть и запоминает тот ответ, в котором действительно оказались
даты. Со следующей проверки используется он. Ничего вписывать руками не
нужно, хотя поле `dates_api_pattern` в конфиге по-прежнему работает.

**Доверие к найденному адресу ограничено по времени.** В нём остаются
параметры момента находки — центр, категория, диапазон дат, — и через месяц
такой адрес может честно вернуть пустой ответ просто потому, что спрашивает
про прошедший интервал. Поэтому раз в `REVALIDATE_EVERY` проверок система
обязана снова пройти длинным путём и обновить адрес. Иначе устаревший
запрос тихо превратился бы в вечное «слотов нет» — худший вид поломки.

## Проверка доставки уведомлений

```bash
python -m app.cli selftest
```

Отправляет получателям то же самое сообщение, что придёт при настоящей
находке, но с пометкой «проверка связи» и без записи в состояние
мониторинга. Нужна потому, что отсутствие слотов — нормальное состояние
системы: без такой команды исправность доставки выяснялась бы в момент,
когда слот наконец нашёлся, то есть слишком поздно.

Частый ответ — `bot was blocked by the user`: Telegram запрещает боту
писать первым, получателю нужно открыть бота и нажать «Запустить».

### Запреты, закреплённые в коде

Система **не обходит CAPTCHA и Cloudflare Turnstile, не меняет IP ради
обхода ограничений и не бронирует слот** (ТЗ §1, §20). Сценарий
останавливается до ввода паспортных данных (ТЗ §14).

Автоматического входа в систему нет вовсе. Это не упущение: форма входа
закрыта Turnstile, кнопка отправки остаётся `disabled` без валидного
токена, и попытки «всё же войти» дали бы ровно тот признак, по которому
VFS блокирует учётные записи, — серию неудачных входов подряд.

## Как работает авторизация

Вход выполняется человеком **один раз**, дальше сессия переиспользуется:

```bash
python -m app.cli add-account --label monitor-1 --username user@example.com
python -m app.cli capture-session --label monitor-1
```

Вторая команда открывает видимый браузер на постоянном профиле
(`PROFILES_DIR/<label>`). Человек сам вводит пароль и сам проходит
Turnstile — программа пароль не подставляет и в браузер не передаёт.
После входа профиль остаётся на диске, и воркер ходит на сайт через него.

Два требования, от которых зависит, проживёт сессия недели или умрёт сразу:

* **каталог профиля должен переживать перезапуск.** В Docker это том
  `profiles`, локально — каталог `PROFILES_DIR`. Потеря каталога означает
  повторный ручной вход;
* **параметры браузера при входе и при проверках должны совпадать.**
  Cloudflare привязывает выданный clearance к отпечатку браузера, поэтому
  локаль, часовой пояс и размер окна заданы одним набором
  `CONTEXT_OPTIONS` в `app/monitor/browser.py` и меняются только целиком.

Когда сессия всё же истечёт, проверки по учётной записи останавливаются,
её статус становится `AUTH_REQUIRED`, и администратор получает уведомление
**сразу**, с первой же неудачной проверки, а не после серии ошибок. Лечится
повторным `capture-session`.

`capture-session` требует настоящего окна браузера, поэтому запускается на
машине с графическим окружением. Для серверного развёртывания профиль
готовится локально и переносится в том `profiles`.

## Быстрый старт (Docker)

```bash
cp .env.example .env   # заполнить BOT_TOKEN, пароли, WEB_SECRET_KEY, CREDENTIALS_KEY
docker compose up -d
```

Миграции применяет отдельный сервис `migrator`; остальные процессы стартуют
только после его успешного завершения.

## Запуск без Docker

Нужны PostgreSQL и Redis на хосте.

```bash
python3.12 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/playwright install chromium

createdb visa_duty                        # роль и база под POSTGRES_* из .env
brew services start redis                 # или иной способ поднять Redis
set -a && . ./.env && set +a
.venv/bin/alembic upgrade head
```

Затем каждый процесс в своём терминале:

```bash
.venv/bin/python -m app.bot.main
.venv/bin/python -m app.scheduler.main
.venv/bin/python -m app.monitor.worker
.venv/bin/uvicorn app.web.main:app --host 127.0.0.1 --port 8000
```

Первый администратор панели (пароль спросит интерактивно):

```bash
.venv/bin/python -m app.cli createadmin --login admin --name "Фамилия Имя" --telegram-id 123456
```

## Состав

| Процесс | Команда | Назначение |
|---|---|---|
| `bot` | `python -m app.bot.main` | Telegram-бот (aiogram 3) |
| `scheduler` | `python -m app.scheduler.main` | Свипы: отбор целей, эскалации, ретраи вебхуков |
| `monitor` | `python -m app.monitor.worker` | Браузерные проверки сайта VFS |
| `web` | `uvicorn app.web.main:app` | Админ-панель (FastAPI + HTMX) |

Мониторинг вынесен в отдельный процесс намеренно: браузер держит память и
живёт секунды, мешать его с лёгкими свипами планировщика нельзя.

## Что осталось

Заполнить в `config/vfs_selectors.json` шаги от начала записи до календаря:
`start_booking`, `select_centre`, `select_category`, `select_subcategory`,
`applicants_input`, `calendar_container`, `available_day`, `available_time`.
Обязательный минимум для запуска — `calendar_container.wait_for`.

Селекторы формы входа уже сняты с живой страницы и проверены. Шаги записи
без входа в аккаунт получить нельзя.

### Как их снять

```bash
python -m app.cli capture-selectors --label monitor-1
```

Команда открывает браузер на уже сохранённой сессии и записывает сырьё:
HTML каждого шага, скриншот и все запросы XHR/fetch вместе с ответами.
Человек просто проходит сценарий в браузере и закрывает окно — снимки
делаются сами, возвращаться в терминал не нужно. Писать CSS-селекторы
вручную тоже не нужно: по записи их выводят потом, спокойно.

Шаги ловятся опросом состояния страницы, а не событием навигации: VFS —
Angular-приложение, и адрес между шагами не меняется.

Запись ложится в `artifacts/selector-capture/<дата>/`:

| Файл | Что внутри |
|---|---|
| `step-NN.html` | разметка шага — из неё берутся селекторы |
| `step-NN.png` | скриншот, чтобы понимать, какой шаг какой |
| `network.json` | все запросы XHR/fetch с ответами |
| `candidates.txt` | адреса ответов, в которых встретились даты |

`candidates.txt` — самое ценное. Если там есть адрес, календарь приходит
готовым JSON, и работает короткий путь: ни кликов по дням, ни `available_day`
не понадобится. Вписывать адрес руками не обязательно — воркер найдёт его
сам на первом же длинном проходе, — но знать заранее, есть ли он вообще,
полезно: от этого зависит, насколько дёшево обойдётся мониторинг.

Команда ничего не отправляет и ничего не заполняет — только смотрит.
Паспортные данные вводить не нужно и нельзя: сценарий останавливается
раньше (ТЗ §14).

## Разработка

```bash
.venv/bin/ruff check . && .venv/bin/mypy src && .venv/bin/pytest
```

Часть тестов работает на живой БД. Без Docker укажите отдельную базу —
тесты пересоздают схему и рабочую БД снесут:

```bash
TEST_DATABASE_URL="postgresql+asyncpg://visa:visa@127.0.0.1:5432/visa_duty_test" .venv/bin/pytest
```

Иначе схему поднимет testcontainers, для чего нужен Docker.
